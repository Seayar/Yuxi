# 故障溯源按 kg5 解析设备类型与设备名

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/knowledge/fault_trace/graph_kg3.py

> 消费方：`fault_trace/workflow.py` 的确认卡片与证据查询、`fault_trace/intent.py` 的卡片渲染。

## 问题

用户提问“110kV银开线故障，请分析原因”，确认卡片把设备类型显示成“变压器”；用户补充“设备类型是输电线路”后，模型确实按补充返回了 `device_type="输电线"`，但重新展示的卡片仍是“变压器”，溯源也按变压器读取现象与原因。

kg5 的只读核对显示两个独立缺陷：

1. **类型解析串到别的设备**：`银开线` 节点（`LGR#SUPLINEYK`）的 `设备分类=输电线路`、`属于→架空线路`；但 `resolve_device_type` 把 `id` 与 `台账ID列表` 用 OR 拼进同一条 `属于` 查询。kg5 有 301 个补充数据设备共用占位台账 ID `补充数据`，等值查询把它们全部命中，再按“名称最小”取到 `变压器`。
2. **设备名匹配不到**：意图识别常保留电压等级前缀（`110kV银开线`、`35kV联络一线`、`35kV开一线`），故障图设备名不带前缀；`find_devices` 的精确与包含查询都返回 0 条，直接判 `device_not_found`。序号口语 `1号主变` 也无法命中图中的 `#1主变…`。

另外，`_prepare_device` 用图谱解析出的类型覆盖了模型识别的设备类型，导致用户的补充即使被模型采用也不会显示。

## 决策

- `resolve_device_type` 按“设备 id 的 `属于` 边 → 台账分类映射 → 台账 ID 的 `属于` 边”顺序解析。台账 ID 是补充数据设备的共享占位值，只有命中唯一类型时才采用；多类型视为无法唯一归属，返回 `(None, None)`，由既有 `device_type_missing` 固定文案收口，不再猜一个类型。
- `find_devices` 先把设备名展开成故障图中的等价写法再匹配：去掉 `110kV`/`35千伏` 等电压前缀；`1号主变` 展开为 `#1主变`、`1#主变`、`1主变`。精确匹配失败后才用包含匹配。
- 确认卡片以模型识别（含用户补充后重新识别）的设备类型为主体；图谱归类不同时并列展示为 `设备类型=输电线路（图谱归类：架空线路）`；识别类型缺失时才用图谱归类补位。溯源证据仍按图谱归类对应的设备类型节点读取，用户确认不改变图谱事实。

## 替代方案

- **让用户确认的类型覆盖图谱类型**：能满足“按我说的来”，但等于让用户自由选择现象与原因集合，绕过图谱证据边界；放弃，改为并列展示冲突。
- **继续把台账 ID 等值查询与设备 id 放在同一条 OR 查询**：共享占位台账 ID 必然串类型，无法靠排序补救；放弃。
- **在前端做名称模糊匹配**：图谱查询与证据读取都在后端，前端匹配不影响实际查询；放弃。
- **修正 kg5 数据（补齐 `属于` 边与真实台账 ID）**：能消除根因，但属于数据治理，超出本次代码修复；本次只让代码在现有数据上 fail-closed 或正确匹配。

## 后果

- 银开线、岭开线等共用占位台账 ID 的设备不再被判成变压器；类型确实无法确定时返回固定 `device_type_missing` 文案，而不是猜一个。
- 带电压前缀与“N号”写法的设备名可以命中；`1号主变` 这类口语可能召回多个同前缀设备，仍走既有的候选消歧卡片。
- 确认卡片同时显示识别类型与图谱归类，二者一致时不重复展示。
- kg5 的数据问题没有被代码修复消除：3002 个设备实例中 2006 个没有 `属于` 边，缺少 `属于` 边且台账分类无映射的设备仍会得到 `device_type_missing`；本次不修改图谱数据。
