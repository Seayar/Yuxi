# 设备识别合并图谱与台账召回，并以用户输入覆盖旧设备

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/knowledge/device_selection.py

## 问题

故障溯源、处置方案生成与设备预测维护都以设备身份作为后续图谱检索的入口。当前召回只在图谱精确或包含查询完全为空时启用名称索引，已有精确命中会将其他相似设备挡在候选之外；设备台账只在解析预测服务 ID 或 Redis 分支 ID 时使用，没有参与候选召回。

设备卡片自由输入还会与上一轮识别结果合并。用户输入候选外的新设备时，只要规则未重新抽出设备字段，旧设备名、类型、电压或位置就会继续参与检索。故障溯源在规则已识别设备时会跳过模型，导致用户的修正文本没有机会覆盖首次规则结果。

这些缺陷会让候选缺少用户真正指的设备，或让用户改填设备后仍按旧设备生成现象、原因、方案和预测结果。

## 决策

1. 事实分层：知识图谱的 `设备实例` 节点仍是可执行候选与后续证据查询的事实源；MinIO 设备台账用于扩大名称、别名、层级和近似名称召回。台账命中必须按台账 ID、名称或层级映射回图谱节点后才进入候选，无法映射的台账行不伪装成可执行设备。
2. 召回合并：三个模块始终合并名称精确/写法变体、名称包含、名称索引近似命中、台账近似命中映射回图谱的记录；词元与设备类型召回只在名称召回为空时补充。候选去重后按匹配质量、台账层级、电压与位置排序，展示上限统一为 24。
3. 用户确认：三个模块每次都通过现有问题卡片让用户确认目标设备；零候选也显示允许自由输入的设备确认卡片。模型只能在有界候选内给出推荐并排在首位，不能代替用户确认或生成设备事实。
4. 用户覆盖：用户在设备卡片自由填写设备名时，本轮输入成为设备身份的唯一来源，清空上一轮的设备名、类型、电压和位置，仅继承任务类型、场景和故障现象等非设备上下文。故障溯源的修正文本必须重新进入解析，不得因首次规则命中而跳过。
5. 可观察性：思考步骤继续披露候选数、模型选择状态和最终设备；召回为空、台账映射为空和用户覆盖旧设备分别留下可诊断日志或结构化事件。

## 替代方案

- 只提高名称索引召回数量：已有精确命中仍会短路召回，无法解决相似候选缺失。
- 直接把台账行作为候选：台账不拥有现象、场景与拓扑证据，选中后仍无法执行后续流程。
- 让模型或用户直接构造设备名与台账 ID：会导致图谱外事实进入证据链，并绕过节点校验。
- 保留上一轮设备字段只为“补齐缺失”：用户明确更换设备时，这会稳定复现旧设备残留，和输入优先级冲突。

## 后果

- 精确命中不再短路相似召回；三个图谱适配器在最多 24 个去重候选内合并图谱名称索引、图谱包含匹配与台账近似命中。台账候选必须映射到图谱设备后才能进入确认卡片。
- 意图字段为空时，三个工具仍用完整原文执行高阈值台账召回；台账命中映射图谱成功后直接进入卡片。同名台账行必须命中台账 ID 或全部站点/开闭所/线路锚点一致；图谱层级为空、共享“主变区域”等子目录或存在同级歧义时一律 fail-closed，避免串站绑定实时值、分支或预测服务 ID。
- 三个工具每次确认设备，唯一候选与零候选一致走问题卡片。模型只决定推荐位，返回清单外 id、null 或失败时仍由用户选择或自由输入。
- 用户自由填写设备名后，上一轮设备名、类型、电压和位置被清除；任务类型、场景和故障现象继续保留。故障溯源首次规则命中不再跳过修正解析。
- 故障溯源删除测试专用 `confirmed_intent` 旁路；真实 LangGraph replay 用例经过实际工具协程、两次 `interrupt`、自由输入换设备、再次确认与最终设备 ID 回读。
- 用户在故障设备卡自由输入后，摘要和推理模型只收到替换后的有效文本；模型若重新带回已被替换的设备名，文案回退到确定性版本。设备确认前不再按旧原文祖先过滤候选。
- 台账搜索使用进程内名称/路径索引和 5 分钟数据缓存。当前真实台账含历史 JSON 语法瑕疵，读取时显式修复并告警；数据 Owner 修复源文件后修复分支自然闲置。
- 卡片展示上限提高至 24，候选区独立滚动，输入与操作栏保持可见；桌面和 390×844 真实组件预览已验证 24 项、中文推荐高亮与零候选自由输入布局。
- 台账无法映射到图谱、图谱无证据或设备类型缺失时仍显式失败，不把台账行伪装成可执行设备。
