# 审查子智能体只做忠实性核验

状态：implemented
类型：architecture
Owner：backend/package/yuxi/knowledge/power_spec/answer.py

## 问题

电力规范的审查子智能体原先同时检查「编造、事实错误、遗漏、无关内容和引用」，其中「遗漏」和「无关内容」都是相对用户问题做的相关性判断。实测一条 35kV 带电作业问题：整理子智能体按输入输出了 12 条条款，审查子智能体把其中 8 条标成「与用户问题无关，应予以剔除」，最终合并只保留了 2 条。检索层已经召回到的条款被审查阶段裁掉，用户看到的是「检索范围小」，而实际原因在答案组织阶段。

审查的职责是核对整理内容是否符合原文，不是判断检索结果是否切题。把条款取舍交给审查，会让审查同时承担相关性和忠实性两种判断，既超出职责，也把检索层的召回结果变成不可预测。

## 决策

1. **审查只核对忠实性**：审查子智能体逐条核对整理内容中的每句话是否能在对应原文中找到依据，只提出三类问题：编造（数字、单位、条件、期限、判据、设备名称、电压等级无原文依据）、语义改变（上限/下限、条件/结论、可选/必须、适用范围、例外、单位被改变）、引用错误（`citation_key` 不对应输入条款）。
2. **审查不得判断相关性**：提示词明确禁止因为「与用户问题无关」「没有直接回答问题」「不是最相关」而提出删除或弱化意见，也禁止评价条款取舍、覆盖范围和答案完整性。
3. **代码兜底丢弃越权意见**：模型仍可能输出旧格式；编排层用 `OUT_OF_SCOPE_REVIEW_KINDS = {"无关内容", "相关性", "切题", "覆盖不足"}` 在进入最终合并前丢弃这些意见，并记录 warning。审查意见只用于修正原文不一致，不能成为删除条款的依据。
4. **合并步骤不得按相关性删条款**：`COMPOSE_INSTRUCTION` 要求逐条保留输入条款，只修正审查意见指出且确实成立的忠实性问题；不得以「与用户问题无关」「没有直接回答问题」「不是最相关」为由删除条款或删减正文。
5. **同步已落库配置**：`ensure_preset` 只在首次落库时写入，已存在的 `power-spec-reviewer` 行不会被代码更新。本次同时把新提示词与描述写回该行，避免代码改了但线上仍用旧职责。

发布策略不变：最终卡片仍以整理/合并输出的条款为准；审查不再提供相关性裁剪意见，因此不会因为审查而丢条款。整理者或合并者如果自行漏掉输入条款，仍可能少于检索证据数，这属于另一个问题。

## 替代方案

1. **保留相关性审查，让合并步骤自行判断是否采纳**：实测合并模型会采纳审查的「无关内容」意见，12 条证据最终只发布 2 条；只靠提示词约束不可靠。
2. **完全删除审查子智能体**：少一次调用和延迟，但失去独立的忠实性核验，编造和语义改变只能靠合并模型自查，正是原设计要避免的。
3. **新增一个独立的相关性审查子智能体**：职责分离更彻底，但增加一次子智能体运行和一套提示词，且用户明确要求审查不判断检索内容是否满足问题；当前不需要。
4. **只在提示词里禁止相关性判断，不加代码过滤**：模型可能继续输出旧 kind；代码过滤是低成本、可观察的兜底。

## 后果

- 审查意见数量会下降；`answer_verified=false` 现在只表示存在忠实性问题（或代码生成的编造/空内容意见），不再表示「条款不切题」。
- 最终卡片数可能比旧行为多，用户看到的条款覆盖更接近检索证据；卡片质量仍取决于整理者的正文提取和合并者的修正。
- 审查不再评价「遗漏」；如果整理者删掉了会改变结论的适用条件，审查应以「语义改变」提出，而不是以「没有回答问题」提出。
- 越权意见被丢弃时只写日志，不进入 `answer_verified` 和用户可见卡片；排查时用日志关键字「超出忠实性范围」定位。
- 预设代码只在首次落库时写入（`ensure_preset` 保留已存在行）。已在当前环境覆写 `power-spec-reviewer` 行的 `description` 与 `config_json.context.system_prompt`；其他环境部署后按 `backend/package/yuxi/agents/presets/subagents/power_spec_reviewer.py` 的当前值执行同一运维。`ensure_preset` 的用户配置保留语义不变。
