# 设备确认按图节点恢复，并优先保留线路杆塔编号

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/knowledge/device_selection.py

## 问题

三个模块在展示设备确认卡前发送 `waiting` 思考事件。用户在卡片中完成选择后，旧等待态仍可能先出现在界面，造成“已经匹配到设备却仍在等待确认”的错误状态。

设备选择依赖工具重放。首次召回与恢复后的召回可能因候选集合变化而不同；旧卡片的图节点 ID 未出现在本次召回列表时，现有逻辑会把它当成自由文本再次执行意图识别。服务器日志已出现 `LGR#...` 被记录为“用户改填设备”，随后设备召回为空并再次弹卡。

线路名与杆塔编号连写时，通用线路规则可能取到“评估联络二线”等错误片段，或只剩“联络二线”；`CN13`、`YN3`、`BN91`、`DN67C` 等具体设备编号因此丢失。模型输出只有“杆塔”类型时，还会覆盖规则已经识别出的具体编号。

## 决策

1. 设备卡片本身就是用户交互，不再额外发射 `waiting` 思考步骤。步骤在卡片前保持 `started`，恢复后只根据真实结果进入 `completed`、`failed` 或 `skipped`。
2. 设备选项 ID 与自由文本使用不同内部类型。选中 ID 未命中重放后的候选集时，按图节点 ID 直接回查设备，并继续走同一业务流程。
3. 选中 ID 不存在于当前图谱时返回固定 `selected_device_unavailable` 结果，不把 ID 当设备名，不再次召回或弹卡。
4. 新增共享的线路杆塔指称解析。线路名进入 `location_hint`；杆塔编号及显式后缀进入 `device_name`；`DN67C相` 作为具体设备名保留，`C相` 同时作为相别上下文。规则识别到具体编号时，模型只返回“杆塔”“线路”等类型词不得覆盖。

## 替代方案

- 在进程内保存首轮候选快照：工具中断恢复可能跨进程、跨 worker，不能作为事实源。
- 让前端回传完整候选设备属性：前端观测值不能替代图谱事实，也会扩大卡片协议。
- 只增加线路正则长度：能扩大命中，但无法解决候选漂移、恢复误判和模型覆盖具体编号。

## 后果

- 用户只确认一次设备，恢复不依赖重算候选的稳定性。
- 设备步骤不再出现无意义的等待态；取消和真正失败仍有明确终态。
- 线路名与杆塔编号分别进入位置和设备字段，候选卡片可展示真实杆塔节点。
- 不新增数据库字段、迁移、配置项或前端接口；既有历史消息中的旧等待态不回溯修改。
- 图节点在用户确认后确实被删除时，本次请求显式失败并要求重新发起，不进入重复弹卡循环。

## 验证

- 三个工具均断言设备确认过程不产生 `waiting` 事件。
- 真实 LangGraph 重放：首轮候选包含 A/B，恢复时召回只含 B，按 A 的节点 ID 直查后只弹一次卡并使用 A。
- 负向用例：选中 ID 在当前图谱不存在时返回固定文案，不再识别 ID 或弹第二张卡。
- `CN13`、`YN3`、`BN91`、`DN67C` 四个输入在处置方案、设备预测和故障溯源中均保留具体编号；模型返回类型词时规则编号获胜。
- 目标知识单元测试、Ruff、工程契约、后端 unit、Web 检查与文档构建按仓库提交门槛执行。
