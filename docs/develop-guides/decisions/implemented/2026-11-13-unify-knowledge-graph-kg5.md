# 故障溯源与处置方案统一读取 kg5

状态：implemented
类型：feature
Owner：backend/package/yuxi/config/options.py

> 其他事实 Owner：故障图谱适配与报告装配在 `backend/package/yuxi/knowledge/fault_trace/`（`graph_kg3.py`、`workflow.py`、`answer.py`），处置方案图名读取在 `backend/package/yuxi/knowledge/maintenance_plan/tool.py`。

## 问题

故障溯源运行时读取 TuGraph `kg3`，处置方案读取 `kg4`，设备预测维护读取 `kg5`。现场已把设备台账、故障现象/原因/触发条件/处置措施与检修作业场景统一录入 `kg5`（2026-11-13 复测）：`kg5` 有 14 个现象节点（其中 `FP_FIRE_1/2/3` 分别是变压器/开关柜/电容器的“燃烧起火”，另有未挂设备类型的旧 `FP_FIRE` 遗留节点）、24 个故障原因、30 个检修作业场景、193 个检修步骤、120 条安全措施、304 条资源需求与 124 条人员需求。`kg3` 只有 4 个现象且全部叫“冒烟”，`kg4` 只保留旧的场景副本。`故障模式` 与 `故障后果` 已从 kg5 移除；现象与设备类型是多对多，kg5 为每个设备类型建立自己的现象节点，原因挂在各自现象节点下。

2026-11-13 的一次起火图片会话在 `kg3` 上被写成“冒烟”：YOLO 正确返回 `fire/燃烧起火`，但 `kg3` 没有“燃烧起火”节点，现象匹配 `matched=false`；报告装配又把展示表的“冒烟”行当成“判定成立的故障现象”。只补数据不能消除这条错误路径，因为 `kg3` 与 `kg5` 都是多现象设备类型；必须同时让定位只使用本次命中的现象。

## 决策

1. **配置默认值与运行态图名切到 `kg5`**：`fault_trace_opts` 的 `graph` 与 `maintenance_plan_graph` 默认值改为 `kg5`，`FAULT_TRACE_GRAPH`/`MAINTENANCE_PLAN_GRAPH` 的兜底值同步；设备预测维护的 `device_prediction_graph` 原本就是 `kg5`。三者仍保留独立图名字段，便于回滚或拆分部署。由于系统配置优先于环境变量，升级部署必须把已保存的 `graph`/`maintenance_plan_graph` 显式改为 `kg5` 或清空后再由环境变量/默认值解析；只改 `.env` 不会覆盖已保存值。
2. **故障图谱适配器只读新 schema**：`graph_kg3.py` 不再查询 `故障模式`/`故障后果`，只走 `设备类型 -[具有现象]-> 故障现象 -[具有原因]-> 故障原因`；现象与原因按节点 `id` 查询，设备类型只取自己的现象节点，因此同名现象只要拆成不同实体就不会跨类型带原因。报告 `meta.graph` 记录实际图名；`meta.schema_version` 仍为 `kg3/v1`，因为它描述标签/关系形状，不描述图实例；`fault_modes` 已从思考步骤数据删除，`impact.consequences` 保留为空以兼容旧客户端。
3. **定位按命中现象收口**：`workflow._match_causal_chain` 在命中现象时，只把命中现象可达的成立原因写入 `state.located_all`，把同一范围的全部原因（含 rejected/unknown）写入 `state.scoped_causes`；verdict、缺失数据、③ 证据与推理文案都使用这个范围。② 展示表只列命中现象（2026-11-16 起，见[故障溯源推理过程只展示命中现象](./2026-11-16-fault-trace-reasoning-only-matched-phenomena.md)），未命中的现象不进入 ③“判定成立的故障现象”。没有命中现象时，按成立原因反推现象集合并带 warning；命中现象但没有任何原因边时范围为空，③ 显示 `—`，不回退到全部原因。
4. **报告装配接收定位现象与范围**：`answer.build_fault_trace_payload` 增加 `location_phenomena`、`phenomenon_name` 与 `located_override` 参数；传入空列表表示“已命中但无成立原因”，渲染为 `—`，不再退回展示表第一行。命中现象下没有成立原因时，`meta.warnings` 记录“未将其它现象的成立原因写入定位”。
5. **处置方案只切图名**：`kg5` 的 `设备实例/设备类型/检修作业场景/检修步骤/安全措施/资源需求/人员需求` 标签、关系与属性与历史 `kg4` 相同；`graph_plan.py` 的查询无需改 schema。`maintenance_plan/tool.py` 的硬编码回退从 `kg4` 改为 `kg5`。
6. **保留配置回指，不保留模式链路**：`kg3`/`kg4` 不删除、不迁移；管理员可以把两个图名字段改回 `kg3`/`kg4`。但当前代码不再读取 `故障模式`：只有现象直接挂设备类型的 kg3 数据能继续溯源；依赖 `故障模式→现象` 的旧数据会返回“未检索到匹配数据”，不会恢复原语义。`fault_trace/seed.py`、`scripts/legacy_kg3_seed/seed.py` 仍是历史导入资产，不参与运行时。

## 替代方案

- **保留 kg3/kg4，向 kg3 补“燃烧起火”数据**：需要维护两份故障现象/原因数据，且无法覆盖 `kg5` 的 11 个现象与新设备类型；现场已声明 `kg5` 是权威数据源，拒绝。
- **把 YOLO 的 fire 映射成 kg3 的“冒烟”**：把更严重的明火降级成冒烟，语义错误；拒绝。
- **只改图名，不改定位收口**：起火图会同时把“冒烟异常”写成成立现象，重现 2026-11-13 的错误；拒绝。
- **给共享现象节点增加设备类型属性**：与现场已采用“按设备类型拆成独立现象实体”的方案重复；代码按节点 id 取原因即可，拒绝。
- **为处置方案保留 kg4 双读**：会引入两套图名与数据同步，当前 `kg5` 已包含全部 30 个场景，拒绝。

## 后果

- 故障溯源默认读 `kg5`：起火图命中当前设备类型自己的“燃烧起火”现象节点（变压器 `FP_FIRE_1`），③ 只列该现象下的火因，不再把“冒烟异常”写成成立现象；冒烟图命中该类型的“冒烟异常”，与 YOLO 类别名一致。
- 现象与设备类型是多对多：同一现象名可以出现在多个设备类型上，但 kg5 已为变压器/开关柜/电容器建立 `FP_FIRE_1/2/3` 三个独立现象节点，原因不跨节点共享；如果数据侧又把多个类型指回同一个现象节点，候选原因会重新变宽。
- `kg5` 仍保留一个未挂设备类型的旧 `FP_FIRE` 节点（带 9 条旧原因边）。当前代码只按设备类型的现象节点查询，不会读到该遗留节点；建议数据侧删除或明确其归属，避免人工按名称查询时误用。
- `故障模式` 与 `故障后果` 已移除：思考步骤不再输出 `fault_modes`，报告的 `impact.consequences` 固定为空，不再发起对应查询；这是 schema 变更，不是链路失败。
- 处置方案输出与 kg4 等价：30 个场景、步骤/安全措施/资源/人员计数一致；设备检索仍要求 `属于` 设备类型边。
- 回滚只改配置，不动代码与数据；回滚到 kg3 时旧图若仍把现象挂在 `故障模式` 下，当前代码不会读取该层，故障溯源只能读取直接挂设备类型的现象/原因链。
