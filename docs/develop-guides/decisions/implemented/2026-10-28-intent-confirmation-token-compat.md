# 意图确认后以用户确认为最终检索条件

状态：implemented
类型：bug-fix
Owner：backend/package/yuxi/knowledge/power_spec/intent.py

## 问题

电力规范检索在用户点“正确，请继续检索”后，仍会返回“意图识别结果与已确认内容不一致，请重新确认检索问题”，并且模型反复重试形成死循环。

根因是设计错误，不是实现细节：确认卡片把“计划指纹”写进选项值，恢复时用它与模型重算的计划比对，不一致就拒绝执行。但意图确认是**人工行为**——用户已经在卡片上确认了设备、电压等级与问题维度；模型重识别只是恢复过程中的一次重算，本不该成为否决用户确认的条件。真实模型在 `temperature=0` 下同提示词重跑也会变化（关键词必变、结构化字段偶发变化），因此这个校验把模型波动直接变成用户阻塞。

## 决策

- **不做任何“用户确认 vs 模型重算”的一致性校验**；确认后的检索条件以用户确认为准。
- 电力规范：确认卡片把**整份计划**（查询类型、设备、电压等级、问题维度、检索关键词、重述句）编码进选项值；恢复时直接用它重建 `PowerSpecQuery` 并检索。没有计划可还原（旧客户端只回传 `confirm`）时，按本次识别结果继续。
- 故障溯源：确认值改为普通 `confirm`；确认后直接按已校验的设备继续。
- 删除 `INTENT_PLAN_CHANGED_MESSAGE` 文案、两个智能体预设中对应的重试禁令，以及指纹/令牌相关的死代码。
- 用户认为识别不对时仍走原有“不正确，我要补充/修改”流程：修正文本回到模型重新识别，重新展示卡片，由用户再次确认。

## 替代方案

- **保留指纹校验、只放宽字段**：仍然把模型重算差异当作用户阻塞，线上已复现，放弃。
- **服务端保存确认快照并在重放时比对**：跨 Run 没有可读快照（工具中断时未返回 `Command`），而且同样是“用模型结果否决用户确认”，方向错误。
- **确认后跳过重新识别**：LangGraph 恢复会重放节点，无法跳过；用确认计划覆盖检索条件达到同样效果，且不依赖框架内部行为。

## 后果

- 用户确认即最终口径：确认卡片上的设备、电压等级、维度与关键词就是检索条件。
- 模型漂移不再阻断流程；旧 checkpoint 中的 `confirm#<hash>` 无法还原计划，会退回本次识别结果继续，不会报错。
- 故障溯源确认值回归普通 `confirm`，确认后使用已解析的设备；模型重识别出不同现象也不会阻断。

## 验证

- `backend/test/unit/knowledge/test_power_spec_tool_intent.py`：确认计划驱动检索（模型重识别成 110kV 时仍按确认的 220kV 检索）、缺失计划回退本次识别、计划编解码与损坏值返回 None。
- `backend/test/unit/knowledge/test_power_spec_intent_interrupt_loop.py`：真实 LangGraph 中断/恢复三轮交互仍按确认继续。
- `backend/test/unit/knowledge/test_fault_trace_confirmation_replay.py`：真实恢复值就是 `confirm`，两条确认路径都判定为确认。
- `backend/test/unit/knowledge/test_fault_trace_tool.py`：重放识别出不同现象时仍产出报告；确认选项值为普通 `confirm`。
- 服务器真实模型验证：复现脚本模拟“用户确认计划 A、重放识别计划 B”，检索条件使用 A，且不再出现“不一致”文案。
