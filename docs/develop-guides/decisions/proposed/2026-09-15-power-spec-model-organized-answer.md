# 电力规范检索的模型参与答案组织

状态：proposed
类型：architecture
Owner：backend/package/yuxi/knowledge/power_spec/tool.py

## 问题

当前电力规范链路的卡片事实字段、条款标题修正、正文片段挑选和 Markdown 格式全部由程序确定性生成，大模型只把工具返回的 `answer_markdown` 原样搬运，`chat_service` 的发布门还会用工具结果覆盖模型输出。这一取舍压住了模型编造和长文输出，但带来三个能力缺口：

- 知识库解析不准确时无法纠正。OCR 造成的条款编号与标题错位、标题缺失或标题取到表格碎片，只能按固定规则回退成编号，无法结合上下文判断。
- 无法按问题挑取相关正文。`_select_relevant_clause_text` 按查询词逐行匹配，命中表格时整块保留，因此卡片正文经常包含整张表而非用户需要的条目。
- 无法跨条款综合。模型不参与组织，只能罗列最多 5 张条款卡片。

同时，链路缺少两个用户要求的环节：验证失败后的模型自迭代，以及迭代超限后询问用户是否接受。当前验证失败直接返回「未检索到资料」，把「无证据」和「证据存在但组织失败」混为一谈。

## 提案

把答案组织权交给模型，用真实的整理与审查两个子智能体形成闭环，确定性代码只保留一道廉价的编造前置门。

意图识别由模型输出结构化意图（问题重述、设备、电压等级、问题维度、检索关键词），规则解析 `parse_power_spec_query` 降为模型失败时的兜底。意图确认卡片展示模型的理解；用户选择不正确并给出修正时，带上一轮意图和用户修正重新识别，而不是终止会话。

证据通过投影校验后进入两段子智能体流程：

- 整理子智能体（`power-spec-organizer`）接收用户问题与受限条款原文，只保留与问题维度相关的内容，可以改写、分条和重新组织语言，使结论简短可读；每条结论必须带 `[source:document_id#clause_no]` 引用。
- 审查子智能体（`power-spec-reviewer`）同时接收原文与整理结果，对抗式核验编造、事实错误、遗漏和引用有效性，输出结构化 JSON 判定。

两者都是真实子智能体运行，经 `SubagentRunService` 启动、`await_agent_run_result` 等待，可审计且可在界面查看。

审查通过即发布模型结果。审查不通过时把审查意见回灌给整理子智能体重试，上限 3 次；超过上限询问用户是否接受：接受则发布并标记未通过审查，不接受则回退到程序生成的固定卡片。

正文文字不再要求逐字不动，改为要求「可溯源」：结论中的数字必须能在原文或用户问题中找到，其余措辞由审查子智能体负责核对。这条数字检查保留为代码实现，因为它挡住的是代价最高的数字类编造，成本极低且不限制措辞。

发布判断保持在 `power_spec/tool.py` 一处：它决定 `answer_markdown` 是模型结果还是固定卡片，并输出 `answer_source` 与 `answer_verified`。`chat_service` 的发布门继续只发布工具给出的 `answer_markdown`，不参与分支。

## 替代方案

1. 维持程序确定性生成。实现最简单、结果完全确定，但正文只能是原文片段堆叠，表格整块出现在卡片里，可读性差且无法按问题浓缩，因此被用户明确否决。
2. 用代码做逐字回溯校验（本提案的早期实现）。能保证文字未被改动，但要求展示正文逐段逐字来自原文，因此禁止改写，与「压缩到可读」直接冲突。
3. 单个模型调用同时负责整理与自查。少一次调用，但同一上下文里的自查容易放过自己的错误，且没有独立审查记录。
4. 整理与审查都由代码实现，模型只做措辞。无法处理解析错位和跨条款综合，等于回到方案 1。

## 风险

模型参与组织会引入一次额外的模型调用，回答延迟增加，且模型输出不稳定导致的迭代会进一步放大延迟。缓解方式是保留固定卡片降级路径，使最坏情况仍能返回可用结果。

LangGraph 在每次 resume 时重新执行整个节点，因此意图确认循环中先前轮次的识别会重跑：确认一次消耗 2 次模型调用，三轮全部否定消耗 9 次。该重跑只影响被否定的路径，代价记为可接受；若要消除，需要把识别结果放进 checkpoint 状态，而工具当前只能读取状态。

Agent 运行上下文在每次 resume 时重建，工具中通过 `setattr(context, ...)` 保存的缓存不跨 resume 生效。因此展示给用户的意图计划与确认后实际使用的计划依赖模型确定性，意图识别固定使用 `temperature=0`。该约束同时说明发布门和结果缓存都只能在同一节点执行内起作用。

模型倾向于用省略号表达「此处省略了无关内容」，这类插入字符会破坏原文回溯。新的架构下这不再由代码强制，但整理提示词仍明确禁止插入省略号、连接词和小标题。

该服务把输入与输出一起计入 `max_model_len`，超出上限的请求返回 400 而不是截断。输出额度必须为提示词留出空间，当前默认 65536。

子智能体在工具内启动并同步等待，父运行在整个等待期间占用一个 worker 槽位。默认 `max_jobs` 为 10，单个用户不会死锁；并发用户较多时父运行会挤占槽位，需要按实际并发评估。

整理与审查子智能体都继承父 Agent 的模型。同一模型承担整理与审查，两者会共享盲区，因此数字前置门不能省略。

审查子智能体的判定质量直接决定重试是否需要发生。提示词把「不确定时按 fail 处理」写成明确规则，代价是可能产生多余重试；每次重试都会重新启动整理子智能体，延迟成倍增加。

子智能体运行依赖父运行的完整运行态。父运行缺少 worker lease 时，子 run 会被执行树回收逻辑取消，因此这条链路必须在真实页面运行中验证，不能用注入的运行记录替代。

本地部署的 Qwen3 系列模型默认先产出思考内容，思考放在响应的 `reasoning` 字段。该服务只识别 `chat_template_kwargs.enable_thinking`，请求体顶层的 `enable_thinking` 字段会被忽略；仅关闭失败的请求会因思考耗尽输出额度而返回空 `content`，使模型路径静默回退到规则解析。关闭思考后意图识别耗时从 50 到 80 秒降到 5 到 7 秒。`max_tokens` 受服务 `max_model_len` 限制，实测该服务接受 100000 而拒绝 102400，因此额度按服务实际上限设置。若延迟仍不可接受，可通过 `POWER_SPEC_INTENT_ENABLED` 显式关闭模型识别。

`clause_no` 允许做字符级修复后，引用键与展示编号可能不一致。若对应关系只存在于单次请求内存中，审计与二次引用会失去可追溯性，因此该映射必须随证据持久化。

关键词由模型生成会扩大召回方差，可能出现规则解析不会犯的错误。需要日志记录实际检索语句，使召回异常可归因。

发布门分流改变了 `chat_service` 的发布语义，属于对模型可见输出边界的修改，需要与 Agent 提示词同步调整，否则提示词仍要求模型原样输出工具卡片。
